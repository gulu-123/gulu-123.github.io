上节 File API 走到“路径 → inode，打开后用 FD 和偏移量读写”。这次想弄清偏移量再往下怎么走。我看图时卡住的是：彩色方块已经画出了文件的块，**索引又在哪？** 方块表示数据在磁盘上的位置，索引是文件元数据中的块号映射。 [前一篇 File API 笔记](../cs537-file-api/)

## 1. 同一个文件，用四种方式回答“第 k 块在哪？”

假设 `/logs/run.log` 占了 7 块。程序看到的是从头到尾的一串字节，文件系统却可以把这些块放在不同位置。**「第 5 块」说的是文件内的顺序，「13 号块」说的是这块数据存在哪里。**

先假设 7 块都挨在一起，从 6 号块开始。那么第 5 块就是 `6 + 4 = 10`。这就是**连续分配**，只要记起点和长度。如果文件要长大，尾部紧邻的位置已经被占用，就得找别的连续空间。

现在换成分散存放，文件的 7 块依次落在 `6、7、8、9、13、14、16`。要找第 5 块，可以这样做：

| 方式 | 怎么找到第 5 块 |
| --- | --- |
| 链式分配 | 从 6 号块开始，每到一块就读它记录的下一块，走到 `6 → 7 → 8 → 9 → 13` |
| FAT | 把后继关系集中存到一张表里，查 `FAT[6]` 得到 7，接着查 7、8、9，最后得到 13 |
| 索引分配 | 为这个文件单独记录块号列表 `[6, 7, 8, 9, 13, 14, 16]`，取第 5 项得到 13 |

**这个块号列表就是图里的索引。** FAT 回答「我现在在这一块，下一块去哪」，文件索引回答「我想读第 5 块，它在哪」。FAT 的分配单位实际叫簇，这里统一用块号方便对照。 [Microsoft FAT 文件系统说明](https://learn.microsoft.com/en-us/troubleshoot/windows-client/backup-and-storage/fat-hpfs-and-ntfs-file-systems)

## 2. 索引放哪，多级索引怎么数？

把 inode 理解成每个文件的一份大小有限的记录，里面有文件长度，也有找数据用的块号。先用小数字看清楚**为什么要多查一层**。假设每个 inode 有 4 个直接指针，每个间接块也只放 4 个块号。

- **第 1 到第 4 块**的块号直接写在 inode 里。对这个日志来说，就是 `6、7、8、9`。
- **第 5 到第 8 块**放不下了。inode 再记一个块号，指向一块专门存地址的**一级间接块**。它的第一项是 13，所以读第 5 块时，先读地址，再去读 13 号块里的数据。
- **第 9 块往后**可以通过二级间接块扩展。二级块有 4 个位置，每个可指向一个一级块。每个一级块又记 4 个数据块号，所以这一层能再覆盖 `4 × 4 = 16` 块。

小文件只用 inode 里现成的直接指针就够了。大文件需要时再分配间接块，多一层可指向更多数据，查找时也多经过一层地址。换回常见的算题数字，如果一个 4 KiB 的间接块里每个块号占 4 字节，那么它能存 1024 个块号。一级覆盖 1024 个数据块，二级覆盖 `1024 × 1024` 个。

## 3. 一次 open、read、write 会碰哪些盘上结构？

继续用 `/logs/run.log`。假设每块 4 KiB，已有的 7 块都写满了。

1. **打开文件。** `open()` 先在根目录里找到 `logs`，再在 `logs` 的目录项里查到 `run.log` 的 inode 号。找到对应的 inode 后，内核建立打开状态，把 FD 交给程序。
2. **读一段数据。** 程序把偏移移到 `16 KiB + 37 字节`，然后调用 `read()`。16 KiB 刚好跳过前四块，所以先查文件的第 5 块，再从块内偏移 37 开始读。按前面的块号列表，实际数据在 13 号块。
3. **追加一整块。** 文件系统先通过数据块位图找到一个空闲块，比如 18 号，并标成已用。然后保存新数据，把 18 记到文件的第 8 项，同时更新文件长度。路径已经存在，这一步不用在目录里再加一个名字。

在这种简单布局里，**目录项**用名字找 inode，**inode 和间接块**用文件内的位置找数据块，**位图**负责找空闲位置。这些结构在磁盘上的布局由**超级块**描述。上面的步骤说的是文件系统需要查什么、改什么。实际访问设备的次数，还要看哪些内容已经在内存里、哪些修改稍后才回写。 [延伸阅读：OSTEP 第 40 章](https://pages.cs.wisc.edu/~remzi/OSTEP/file-implementation.pdf)

## 4. FFS 和缓存分别省了什么？

**FFS 管磁盘布局。** 它把磁盘划成柱面组，尽量把同一文件的 inode 和数据、同一目录下相关文件的数据结构放在附近。访问仍需要读盘时，好的布局能减少机械盘寻道。 [OSTEP 第 41 章](https://pages.cs.wisc.edu/~remzi/OSTEP/file-ffs.pdf)

**页缓存管内存里的文件数据。** 普通缓冲读命中时，文件数据可以直接从内存取得。缓冲写可先修改内存中的页，把它们标成脏页再回写。所以需要持久化时，还要看 `fsync()` 等接口的完成结果。 [Linux 页缓存文档](https://docs.kernel.org/mm/page_cache.html)

对话里问“LLM 的 cache 是同一个吗”，可以从缓存的内容和命中时省下的工作来看。

| 缓存 | 保存什么 | 命中时省什么 |
| --- | --- | --- |
| OS 页缓存 | 文件内容的数据页 | 读取底层存储 |
| LLM KV cache | 已处理 token 在各注意力层的 Key、Value | 生成下一个 token 时重算历史 token 的 K、V |
| LLM 前缀缓存 | 可复用前缀的 KV 状态 | 不同请求共享相同 token 前缀时，省去这段前缀的预填充计算 |

页缓存和 KV cache 都用更多内存换取少做一部分工作，具体省下的是设备读取或模型计算。 [Hugging Face KV cache 说明](https://huggingface.co/docs/transformers/main/en/cache_explanation) · [vLLM 前缀缓存文档](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)
