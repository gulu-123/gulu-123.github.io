上节 File API 走到“路径 → inode，打开后用 FD 和偏移量读写”。这次想弄清偏移量再往下怎么走。我看图时卡住的是：彩色方块已经画出了文件的块，**索引又在哪？** 方块表示数据在磁盘上的位置，索引是文件元数据中的块号映射。 [前一篇 File API 笔记](../cs537-file-api/)

## 1. 同一个文件，用四种方式回答“第 k 块在哪？”

用课件里的文件 B 手推。它的块依次在 `6, 7, 8, 9, 13, 14, 16`。想找第 5 块，也就是从 0 开始的逻辑块 4。

| 分配方式 | 记录什么 | 怎么找第 k 块 |
| --- | --- | --- |
| 连续分配 | 起始块和长度 | 起始块加 k。增长时需要紧邻的空闲块，容易受外部碎片影响 |
| 链式分配 | 首块，每块存后继块号 | 从首块沿链走 k 步 |
| FAT | 目录项记首簇，共享表记每个簇的后继 | 从 6 出发，查表走 `6 → 7 → 8 → 9 → 13`。缓存 FAT 能减少查表 I/O，仍要沿链前进 |
| 索引分配 | 按文件保存逻辑块号到实际块号的映射 | 直接取文件 B 的索引 `[6, 7, 8, 9, 13, 14, 16][4]`，得到 13 |

**FAT 的下标是当前簇号，表项是下一簇号。索引分配的下标是文件内的逻辑块号，表项是所查的块号。** 这里用课件块号作示意，FAT 实际以簇为分配单位。离散分配可以利用分散的空位，文件的块仍可能分散，顺序读也仍会受物理布局影响。 [Microsoft FAT 文件系统说明](https://learn.microsoft.com/en-us/troubleshoot/windows-client/backup-and-storage/fat-hpfs-and-ntfs-file-systems)

## 2. 索引放哪，多级索引怎么数？

简单的指针数组可以直接放在 inode 里。经典 Unix 混合索引用**直接指针**服务小文件，再用**间接块**扩展。一级间接块存数据块指针，二级间接块指向一级间接块。间接块也占磁盘空间，只有需要时才分配。

手算一个教学模型：块大小 4 KiB，每个块号占 4 字节，inode 有 12 个直接指针、一个一级和一个二级间接指针。一个间接块可存 `4096 / 4 = 1024` 个块号。

- 直接、一级、二级分别覆盖 `12`、`1024`、`1024²` 个数据块。
- 偏移 `12 × 4096 + 37` 落在逻辑块 12、块内 37 字节处，正好走一级间接块的第一项。
- 只算索引覆盖的文件数据，最多是 `(12 + 1024 + 1024²) × 4 KiB`，即 4 GiB + 4 MiB + 48 KiB。再加一个三级间接指针，就多覆盖 `1024³` 个数据块。间接块本身的空间开销另算。

## 3. 一次 open、read、write 会碰哪些盘上结构？

用教材的教学文件系统 vsfs 来记。**超级块**描述整个文件系统的布局，**inode 位图和数据块位图**分别记录哪些 inode、数据块可分配，**inode 表**存元数据和块映射，**数据区**存文件内容、目录项等。

- `open("/a/b")` 从根目录逐级查名字，读取目录项和相关 inode，找到目标后建立打开状态。
- `read(fd, …)` 从打开状态取得文件偏移，用 inode 的块映射找到数据。逻辑块号是 `floor(偏移 / 块大小)`，块内位置是 `偏移 % 块大小`。
- 向已有文件追加一个新数据块时，通常要分配空闲块、写入数据、更新 inode 的映射和长度。跨过索引边界时，还可能新建间接块。创建新文件时则要额外分配 inode，并在父目录加入名称。

这些步骤涉及哪些结构，可以逐项追踪。实际发生几次设备 I/O，还要看缓存命中和何时回写。追加操作改动了多个块，如果掉电时只写完其中几个，就进入后续的崩溃一致性问题。 [OSTEP 第 40 章](https://pages.cs.wisc.edu/~remzi/OSTEP/file-implementation.pdf)

## 4. FFS 和缓存分别省了什么？

**FFS 管磁盘布局。** 它把磁盘划成柱面组，尽量把同一文件的 inode 和数据、同一目录下相关文件的数据结构放在附近。访问仍需要读盘时，好的布局能减少机械盘寻道。 [OSTEP 第 41 章](https://pages.cs.wisc.edu/~remzi/OSTEP/file-ffs.pdf)

**页缓存管内存里的文件数据。** 普通缓冲读命中时，文件数据可以直接从内存取得。缓冲写可先修改内存中的页，把它们标成脏页再回写。所以需要持久化时，还要看 `fsync()` 等接口的完成结果。 [Linux 页缓存文档](https://docs.kernel.org/mm/page_cache.html)

对话里问“LLM 的 cache 是同一个吗”，可以从缓存的内容和命中时省下的工作来看。

| 缓存 | 保存什么 | 命中时省什么 |
| --- | --- | --- |
| OS 页缓存 | 文件内容的数据页 | 读取底层存储 |
| LLM KV cache | 已处理 token 在各注意力层的 Key、Value | 生成下一个 token 时重算历史 token 的 K、V |
| LLM 前缀缓存 | 可复用前缀的 KV 状态 | 不同请求共享相同 token 前缀时，省去这段前缀的预填充计算 |

页缓存和 KV cache 都用更多内存换取少做一部分工作，具体省下的是设备读取或模型计算。 [Hugging Face KV cache 说明](https://huggingface.co/docs/transformers/main/en/cache_explanation) · [vLLM 前缀缓存文档](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)
