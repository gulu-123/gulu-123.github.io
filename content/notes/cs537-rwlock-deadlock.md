今天最卡的是：**T3 在等读者离开，T4 明明也是读者，为什么也要等？** 读写锁允许多个读者共享访问，写者独占。T4 能否加入这批读者，还取决于锁的准入策略。

## 1. 从首读者和末读者，到写者优先

读者优先版本有两份状态。`lock` 保护读者计数 `readers`，`writelock` 则由一批读者或一个写者占用。首个读者在 `0 → 1` 时对 `writelock` 执行 `sem_wait()`，最后一个读者在 `1 → 0` 时执行 `sem_post()`。首读者与末读者可以是不同线程，所以例子用的是允许跨线程归还许可的信号量。写者直接等待 `writelock`。读者连续加入时，计数可能一直降不到 0，写者就可能饥饿。 [OSTEP §31.5](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-sema.pdf)

写者优先版本增加了活跃与等待计数。按对话中的调度手推，`OKToRead`、`OKToWrite` 初值都是 0：

| 步骤 | 谁在等、谁能推进 |
| --- | --- |
| T1、T2 请求读锁 | 无活跃或等待的写者，两者都获准读 |
| T3 请求写锁 | 还有两个活跃读者，登记为等待写者，放开内部 mutex 后等 `OKToWrite` |
| T4 请求读锁 | T3 已在等待，T4 登记为等待读者，放开 mutex 后等 `OKToRead` |
| T1、T2 依次离开 | 最后一个离开的读者登记写者获准，再发一个写许可，T3 可以写 |
| T3 写完 | 这个时序里已无等待写者，T3 发放读许可，T4 可以继续 |

**T4 卡在等待写者计数上。** 内部 mutex 只保护计数与放行决策。发许可前要把名额记入活跃计数，等许可前要释放 mutex，其他线程才能登记退出并发出许可。这里 T1、T2 仍可退出，所以是正常阻塞。持续到来的写者可能让读者饥饿，写者优先本身也没有承诺 FIFO。

## 2. 死锁就顺着「谁等谁」画一圈

假设 A 持有 `L1` 等 `L2`，B 持有 `L2` 等 `L1`，两人都要拿齐锁才继续。A 等 B，B 又等 A，谁都走不到解锁处。这与[信号量笔记里的哲学家就餐](../cs537-semaphores/)是同一种环。

四个必要条件依次是：

1. **互斥**。资源同一时刻只能被一个线程独占。
2. **持有并等待**。线程保留已有资源，同时请求其他资源。
3. **不可抢占**。别人无法强行收走它已持有的资源。CPU 时间片仍可以被抢占。
4. **循环等待**。沿着等待关系最终回到起点。

处理两把锁时，给所有路径规定同一种顺序，例如总是先 `L1` 后 `L2`。锁的编号沿等待链严格增加，环无法闭合。也可以用 `trylock`，第二把锁拿不到时释放第一把，稍后重试。若双方反复同步退让，可能活锁。**死锁看一组线程能否推进，饥饿看某个线程是否一直得不到机会。** [OSTEP §32.3](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf)

## 3. 并发出错时，先区分缺了哪条保证

| 对话中的例子 | 复习时先问什么 |
| --- | --- |
| 检查指针后再使用，中间被另一线程改掉 | **原子性**。检查到使用之间谁能改状态？若指向对象还可能被释放，还要保护其生命周期 |
| 创建线程返回后才保存句柄，新线程已经尝试读取它 | **顺序性**。怎样确保初始化或发布先于读取？可用同一同步协议建立这个顺序 |
| 用 CAS 写回 `old + delta` | **原子更新**。比较的预期值应是这次读到的 `old`。失败后刷新旧值再算。CAS 重试式原子加法在相应原子操作为 lock-free 时可保证系统整体进展，单个线程仍可能反复失败 |

CAS 的返回约定见[之前的 Locks 笔记](../cs537-locks/)，检查后使用和线程启动的例子可回看 [OSTEP §32.2](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf)。

复习时遮住答案试着讲一遍：**T3 为什么等？T4 为什么等？谁能让它们继续？**
