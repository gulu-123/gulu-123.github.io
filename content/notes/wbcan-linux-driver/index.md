在 Workbench 移动机器人项目中，我参与 Linux 驱动开发，围绕 wbcan 虚拟 CAN 驱动、故障注入、发送队列与资源管理，以及 SocketCAN 到 ROS 2 的诊断链路开展工作。这篇笔记把相关知识串起来，方便以后阅读发送、停机和恢复路径时快速定位问题。

[项目介绍]({{< relref "/projects/workbench-mobile-home-robot.md" >}}) · [项目源仓库](https://github.com/Quchaosheng/workbench-mobile-home-robot)

源码阅读基于 2026 年 11 月 13 日整理时的仓库版本 `16fd1e7a43f8`，主要入口为 `kernel/wbcan/wbcan.c`。下文结合该版本实现总结机制；具体函数与接口以对应版本源码为准。

## 1. 为什么把故障放到 CAN 驱动层

应用通过 SocketCAN 访问 CAN 网络接口。驱动向上遵循 Linux CAN 子系统语义，上层设备协议和 ROS 2 运行时负责解释帧的业务含义。

```text
ROS 2 / 设备运行时：命令、超时、重试、状态发布
        ↓
用户态 SocketCAN：AF_CAN socket，发送与接收 CAN 帧
        ↓
Linux CAN 核心与网络栈：过滤、回环、错误帧、队列
        ↓
wbcan：虚拟 CAN 网络设备，可配置故障
```

正常收发只能覆盖一部分路径。上层还需要面对“写入被接受但帧没有交付”“暂时不能继续发送”“设备进入 bus-off”等情况。wbcan 通过内核中的状态变化、错误帧和统计，把这些异常送到标准接口上，让恢复逻辑面对可重复的输入。

wbcan 是软件故障测试设备。这里整理的是内核接口、状态和恢复机制；真实控制器的寄存器、IRQ、DMA、总线仲裁时序与物理性能需要在目标硬件上另外验证。

## 2. 把注册、启停和卸载分开看

对应源码入口：`wbcan_init()`、`wbcan_open()`、`wbcan_stop()`、`wbcan_exit()`。

| 阶段 | 关键动作 | 要检查的问题 |
| --- | --- | --- |
| 模块初始化 | `alloc_candev()`、配置回调、`register_candev()`、建立 debugfs | 任一步失败，前面取得的资源是否回收？ |
| 接口启动 | `open_candev()`、设置可工作状态、启动 TX 队列 | 状态和队列是否一起进入可发送状态？ |
| 接口停止 | 禁止新发送、同步在途路径、设置 STOPPED、`close_candev()` | 已排队的恢复工作是否还可能唤醒设备？ |
| 模块卸载 | 撤销 debugfs、注销网络设备、释放私有资源 | 是否仍有回调能访问即将释放的对象？ |

**接口已经注册，不代表接口已经启动；接口停用，也不等于模块已卸载。** 这几个阶段的可见性和资源责任不同。

该版本在模块加载时创建单个 `wbcan0`，由模块卸载移除。复现时先看模块生命周期，不能直接假设它支持 `ip link add ... type wbcan`。

## 3. 先弄清 skb 归谁，再看返回码

发送入口是 `wbcan_start_xmit()`。阅读每个分支时，先问：**返回之后，这个 skb 由谁继续持有和释放？**

| 返回结果 | 所有权与处理责任 |
| --- | --- |
| `NETDEV_TX_OK` | 驱动已接管该 skb，需要完成消费、释放或向后续路径转交 |
| `NETDEV_TX_BUSY` | 驱动没有接管，网络栈保留 skb，以便后续重试；驱动不能提前释放它 |

`NETDEV_TX_OK` 表示驱动接受了处理责任。故障注入可以在接受后主动丢弃帧，因此这个返回值并不能证明对端收到了帧。

阅读时可按下面的所有权关系检查；这是逻辑示意，不是完整驱动实现：

```text
暂时没有发送资源 → 停止队列 → 保留 skb → 返回 BUSY
接受并主动丢弃   → 更新相应统计 → 释放 skb → 返回 OK
接受并本地回环   → 转换或复制 skb → 交给接收路径 → 返回 OK
```

位翻转分支还涉及数据共享：如果其他路径持有同一数据区的克隆，直接改写可能影响它们。该版本通过 `skb_copy()` 获得独立数据，并保留来源 socket 关联，使回环接收继续遵守 SocketCAN 的语义。

## 4. 背压是一组队列动作

当发送资源暂时不足时，只有一个 BUSY 返回值还不够，还需要明确什么时候停止提交、由谁通知资源恢复。

- `netif_stop_queue()`：停止继续向该发送队列提交。
- `NETDEV_TX_BUSY`：本次 skb 尚未被驱动接管。
- `netif_wake_queue()`：资源重新可用后，让队列继续运行。

wbcan 的 `tx-full` 分支模拟瞬时拥塞：停队列、报告故障，再立即唤醒并返回 BUSY。这里的立即唤醒是测试模型的选择。真实硬件通常要等发送完成或描述符回收，确认有可用资源后才能唤醒。

还要避免把 BUSY 重试计为多次成功发送。该版本在接受帧之后才增加正常接受路径的发送计数，使“调用发送入口”和“接受一帧”保持区别。

这和[有界队列中的等待与唤醒]({{< relref "/notes/cs537-queue.md" >}})有共同点：通知只促使执行继续，真正决定能否推进的是资源和状态条件。

## 5. bus-off 恢复要同时考虑状态、队列和停机

bus-off 涉及 CAN 控制器状态变化。故障路径要让 CAN 核心和用户态能观察到相应状态、错误和计数；恢复时则通过 CAN 核心的 restart 路径进入 `wbcan_set_mode()`。

整理这条路径时，抓住三个条件：

1. **进入故障后停止发送。** 状态已经不可发送时，队列也应停止。
2. **恢复之前重新检查状态。** `CAN_MODE_START` 回调需要确认当前仍是 BUS_OFF，避免覆盖已经发生的停止操作。
3. **停机必须处理在途恢复。** 禁止新发送以后，还要同步恢复工作，防止接口 down 之后被旧工作重新唤醒。

该版本恢复时还清除已配置的故障，避免下一帧又被同一故障命中，使恢复测试的条件可控。不同测试如果需要持续故障，应明确配置，不能把一次恢复后的再次失败混成同一个结论。

分析这类问题时，把“状态写入”“队列停启”“异步工作完成”放到同一条时间线上，比只盯住某一个状态字段更容易发现竞态。

## 6. 并发保护要覆盖状态之间的关系

发送路径、debugfs 配置和状态读取、恢复回调、接口停止可能交错执行。需要保护的不只是单个整数，还有“设备状态与队列状态是否一致”这样的关系。

| 机制 | 在该实现中关注的作用 |
| --- | --- |
| 私有 spinlock | 保护故障配置、计数及状态快照中的共享字段 |
| TX 路径同步 | 协调发送、停机和恢复对队列与设备状态的访问 |
| `READ_ONCE()` / `WRITE_ONCE()` | 约束单个共享字段的访问，不能代替跨字段同步 |
| 快照后输出 | 在短临界区复制状态，解锁后格式化 debugfs 输出 |

持有自旋锁时不能执行可能睡眠的操作。状态输出也应缩短占锁时间，避免为了读取诊断信息而长时间阻塞数据路径。

这里可以和[锁与线程调度]({{< relref "/notes/cs537-locks.md" >}})一起理解：锁保护的是约定中的共享状态；选择锁之前，先找出谁会访问它、处于什么上下文、需要维护什么不变量。

## 7. 故障注入要能解释“发生了几次、影响了什么”

wbcan 的 debugfs 配置支持故障类型、次数、跳过的匹配帧数、CAN ID 匹配，以及位翻转的位置。它使异常可以按条件触发，而不依赖偶然出错。

| 场景 | 要关注的知识点 |
| --- | --- |
| drop-tx / drop-rx | 接受、发送统计和最终交付之间的区别 |
| bit-flip | 独立数据副本、载荷变化及上层协议校验 |
| tx-full | BUSY 分支的 skb 所有权、队列停止与唤醒 |
| bus-off | CAN 状态、错误帧、停止发送与 restart |

debugfs 用于测试和调试，生产配置应继续遵循 SocketCAN 等标准接口。诊断时把网络统计、`ethtool -S` 的驱动计数和 debugfs 状态快照结合起来看：匹配到多少候选帧、实际注入多少次、接收多少帧、是否发生恢复，分别回答不同的问题。

例如，“drop-tx 生效”不能只看应用没有收到数据，还应核对故障配置、命中计数与接收端观察，排除接口未启动或过滤条件不匹配。

## 8. 跨层诊断：发送、ACK、完成分别证明什么

从驱动走到机器人业务时，最容易混淆的是不同层次的成功：

| 观察 | 能说明什么 | 后续还要看什么 |
| --- | --- | --- |
| 用户态发送调用成功 | 本次写入按接口语义被接受 | 驱动是否交付、对端是否处理 |
| 驱动回环或接收路径出现帧 | 本地软件收发路径产生了对应观察 | 真实对端与物理链路证据 |
| 设备协议 ACK | 对端按协议确认了相应阶段 | ACK 定义的是接受还是完成 |
| ROS 2 Action 终态 / TaskEvent | 运行时的任务状态与协议结果 | 执行器运动或目标达成的观察证据 |

这里的协议 ACK 指设备应用协议的确认消息，要与 CAN 数据链路层的 ACK 位区分。

分析超时、重试或 STOP 抢占时，需要沿着命令标识、帧收发、ACK、运行时状态追踪同一次操作。重试是否会重复执行、STOP 后是否仍有旧回复、恢复后状态是否重新发布，都需要对应层的证据。

这次项目形成的阅读顺序是：**先看分层与接口，再沿 skb 所有权追踪发送，最后把队列、设备状态和异步工作的生命周期放在一起检查。** 正常收发之外，错误分支与恢复路径同样决定驱动能否被上层可靠使用。
