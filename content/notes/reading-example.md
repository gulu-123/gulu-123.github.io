学习笔记可以从一个很小的问题开始。这篇文章演示正文、代码、表格、目录和引用的排版，也提供一份日后记录时可以沿用的结构。

## 先写下一个具体问题

比起只留下主题名称，更有用的开头是：**这次到底想弄明白什么？**

例如，阅读一段源码时，可以先写清楚自己正在追踪的行为，以及希望找到的入口。问题不必很大，能通过一小段阅读或一次实验推进就好。

> 一篇记录解决一个具体问题。暂时没有想明白的地方，也可以原样留下。

## 给过程留一份环境记录

下面只是记录格式示例。实际使用时，应填写自己运行得到的信息，而不是把示例当作实验结果。

| 项目 | 应填写的内容 |
| --- | --- |
| 系统与版本 | 实际使用的发行版与内核版本 |
| 源码版本 | 对应的 tag 或 commit |
| 阅读入口 | 本次追踪的文件和函数 |
| 实验目标 | 想观察或验证的现象 |

如果执行了命令，可以保留命令和原始输出。示例中的 `uname -r` 用于查询当前运行的内核版本：

```bash
uname -r
```

## 代码与观察放在一起

这里用一小段与内核无关的 C 代码演示高亮和复制功能。它不是内核源码，也不代表已完成的项目。

```c
int sum(const int *values, int count)
{
    int total = 0;

    for (int i = 0; i < count; ++i) {
        total += values[i];
    }

    return total;
}
```

记录真实代码时，可以在代码块后紧接着回答三个问题：

1. 这一段在做什么？
2. 哪些输入或前置条件会影响结果？
3. 观察到了什么，有哪些证据支持当前理解？

把**运行结果**和**自己的推断**分别写清楚，回看时更容易继续思考。

## 最后留下下一步

- 今天的问题是否已经得到回答？
- 哪一部分仍然不确定？
- 下一次准备读哪个文件，或补哪个实验？

笔记不需要一次写成完整教程。保留具体的问题、过程与下一步，就已经有了可以继续积累的起点。[^record]
