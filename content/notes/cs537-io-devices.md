看课件的时间轴时，我先问 **DMA 到底好在哪**，后来又问 **I/O 调度明明是软件，为什么要跟磁盘和缓存一起讲**。可以沿着一次磁盘写来理解：驱动提交请求，硬件搬运并处理数据，系统确认完成，每一步的开销和保证都不同。

## 1. 一次 I/O 有三个独立的问题

课件的抽象设备有三类寄存器。驱动读 `STATUS` 看设备是否忙，写 `DATA` 交付数据，写 `COMMAND` 启动操作。最朴素的写协议是：轮询到空闲 → CPU 写数据 → 发命令 → 再轮询完成。把这条路径拆开，就能看出每种机制改了哪里。 [OSTEP《I/O Devices》](https://pages.cs.wisc.edu/~remzi/OSTEP/file-devices.pdf)

| 要解决的问题 | 两种常见机制 | 复习时追问 |
| --- | --- | --- |
| CPU 怎样访问设备寄存器 | 端口 I/O、MMIO | 这次读写被送到哪个设备？ |
| 谁搬有效载荷 | PIO（CPU 搬）、DMA（硬件搬） | CPU 是否要逐次读写数据？ |
| 怎样知道完成 | 轮询、中断 | CPU 要反复读状态，还是由设备通知？ |

对照时间轴手推一次 **DMA + 中断**。进程 A 发起写入，驱动准备缓冲区和 DMA 地址，再提交请求。设备或 DMA 控制器搬运数据，A 若需要同步等结果，可以阻塞，CPU 此时能去跑 B。收到完成中断后，驱动检查状态并通知等待者，调度器再决定 A 何时运行。**DMA 省掉 CPU 逐次搬运的工作，中断省掉反复查询完成状态的工作。** 两者可以独立使用，DMA 完成也可以靠轮询确认。

短等待时，主动轮询可能省掉中断处理的开销。通知过于频繁时，可以合并中断来降低开销，代价是部分请求的完成通知会更晚。DMA 主要减少 CPU 开销并让计算和传输重叠，单次 I/O 延迟仍取决于设备和请求。

## 2. 学过虚拟内存，为什么还要学 I/O 寻址？

地址翻译解决的是**CPU 虚拟地址怎样映射到物理地址**。MMIO 关心的是**该物理地址范围由什么硬件响应**：命中设备窗口时，读写会到控制器寄存器，而普通 RAM 地址由内存响应。x86 的 `in/out` 则通过独立的 I/O 端口空间访问设备。

在 Linux 驱动里，通常先映射寄存器资源，再用 `readl()/writel()` 等接口访问。给 DMA 硬件的则是 **DMA API 提供的设备可用地址**。CPU 虚拟指针、CPU 物理地址、DMA 地址要分开记，IOMMU 或总线桥可以让后两者不同。 [Linux 设备 I/O 文档](https://docs.kernel.org/driver-api/device-io.html) · [DMA 映射指南](https://docs.kernel.org/core-api/dma-api-howto.html)

## 3. 为什么块层调度要看硬件？

拿普通文件写入最终形成的块 I/O 作例子，路径可以简化为 `应用 → 文件系统 → 通用块层 → 设备驱动 → 控制器`。文件系统把文件读写转换成块请求，块层组织队列并按条件合并或调度，驱动把请求转换成设备理解的命令。

**I/O 调度决定软件队列里的请求如何发出，硬件决定不同顺序会付出什么代价。** HDD 的寻道和旋转让访问位置影响延迟，相邻请求更值得合并。SSD 没有机械寻道，多个硬件队列可以并行提交请求，Linux 的 `blk-mq` 就是为这类并行能力设计的。 [Linux blk-mq 文档](https://docs.kernel.org/block/blk-mq.html)

## 4. 写完成，数据到哪一层了？

设备侧缓存由控制器管理，和系统 RAM 里的页缓存各在一层。读路径上，HDD 可以预读相邻扇区，后续请求若命中，可省去再次等待盘片转动。 [OSTEP《Hard Disk Drives》](https://pages.cs.wisc.edu/~remzi/OSTEP/file-disks.pdf)

写路径上，普通缓冲写的 `write()` 返回可以只表示内核已接收数据。设备启用易失写缓存时，块请求也可能在数据仍留在控制器缓存时就报告完成。中间件需要持久性时会关注 `fsync()` 的结果，存储栈在需要时借助设备缓存 flush 或 FUA 确保相应写入到达非易失介质。 [Linux 设备写缓存控制](https://docs.kernel.org/block/writeback_cache_control.html)

按自己的方向回看：**驱动和 BSP** 先追寄存器、IRQ、DMA 地址和缓冲区归属，**中间件** 先追一次写入何时返回、何时满足持久性要求。HDD 是理解寻道代价和块层调度的例子。之后看 CAN 驱动也可以沿用“谁提交、谁拥有缓冲区、完成意味着什么”这几个问题，具体队列与协议则要按设备类型看。 [Linux CAN 驱动笔记](../wbcan-linux-driver/)
