今天学习 **CS537 Fall 2019 的 Concurrency: Locks**。围绕提问留下这条主线：**锁限制谁能进入临界区；调度器决定谁在 CPU 上运行。**

## 1. T1 恢复后，为什么还是旧值？

用共享变量 `x = 0` 手推一次（教学执行模型）：

| 顺序 | T1：加 1 | T2：加 2 | 共享内存 x |
| --- | --- | --- | --- |
| ① | 读到自己的寄存器：0 | | 0 |
| ② | 被切走 | 读 0，加 2，写回 | 2 |
| ③ | 恢复自己的寄存器：仍是 0 | | 2 |
| ④ | 加 1，写回 | | **1** |

**上下文切换保存、恢复的是各线程自己的寄存器现场，不会自动把共享内存的新值重新读进寄存器。** 所以 T1 覆盖了 T2 的更新，正确的串行结果本应是 3。

根因是**共享数据的读—改—写缺少同步**，不是寄存器私有本身有错。

## 2. 加了锁，还能发生上下文切换吗？

**能。持锁线程被切走，锁仍由它持有，其他遵守同一把锁的线程不能进入临界区。**

- 原子抢锁：保证共享锁状态的检查、修改不可分割，**不等于整个 `lock()` 函数关闭调度**。
- 用户态自旋：没拿到锁就循环尝试，仍可能被抢占。
- 阻塞等待：抢不到时可以睡眠，让其他线程运行；无竞争的 mutex 快路径不必发生切换。

调度策略可以公开，但不能依赖某次切换的精确时刻来保证正确性。

## 3. 普通 flag、XCHG、CAS 到底差在哪？

下面这个简单方案失败，因为两个线程可能同时读到 0，然后都把它写成 1：

```c
// 错误示意：检查与占用是分开的
while (flag == 1) { }
flag = 1;
```

XCHG / CAS 把抢锁需要的动作合成原子操作。以下是**课程语义伪代码**，不是完整的 C/C++ 锁实现，也未做运行实验：

```c
// 初始 flag = 0；0 表示空闲，1 表示占用
void lock_by_xchg(void) {
    while (XCHG(&flag, 1) == 1) { }
}

void lock_by_cas(void) {
    while (CAS(&flag, 0, 1) != 0) { }
}
// 此处 CAS 约定返回旧值；不同 API 的返回约定可能不同
```

| 操作 | 原来是 0 | 原来是 1 |
| --- | --- | --- |
| `XCHG(&flag, 1)` | 写 1，返回 0：拿到锁 | 写 1，返回 1：继续等 |
| `CAS(&flag, 0, 1)` | 比较成功，写 1，返回 0 | 比较失败，不改值，返回 1 |

**记忆点：看返回的旧值判断“我有没有抢到”，不是看交换之后的值。**

课件的 C 伪代码只描述 XCHG 的含义，照抄普通读写并不会获得原子性。汇编约束速记：`"+m"` 是读写内存，`"=a"` 是累加器输出，`"1"` 复用编号 1 的操作数；`asm volatile` 不等于完整同步屏障。[¹](#参考)

**不是所有 load/store 算法都不成立**：Peterson 的“举手＋谦让”依赖双线程、顺序一致和原子读写；普通 C 变量照抄版不能直接用于现代机器。

## 4. 查询不改链表，为什么还要锁？

插入时，两个线程更新 `head` 可能丢节点；查询时，**拿到指针 → 另一线程删除并释放节点 → 继续解引用**，可能访问已释放内存。

“没有 Delete 就不用锁”还依赖课件的发布与可见性假设。真实 C/C++ 中，并发插入和普通指针读取也可能构成数据竞争。**只读不等于无需同步；同一把锁要由读写双方共同遵守。**

## 5. 自旋是等待方式，票据是排队方式

我起初把“普通 flag 失败”理解成“自旋锁不安全”。其实要分开看：

- **互斥**：能否同时进去两个人？
- **进展、无饥饿**：有人能推进，是否还可能有人一直等？
- **性能**：等待消耗了多少 CPU 和调度成本？

多核、临界区短且持锁者能继续运行时，自旋可能更划算；等待长或单核竞争时，空转代价更明显。**对话中的纳秒数不是通用结论。**

票据锁再加上“取号—叫号”：

```c
// 语义伪代码：初始 ticket = turn = 0
my_ticket = FetchAndAdd(&ticket);  // 原子取号，返回旧值
while (turn != my_ticket) { }     // 仍在自旋
// 临界区
turn = turn + 1;                  // 持锁者交给下一号
```

**按取号顺序服务，仍然自旋。** 无饥饿依赖持锁者最终释放、排队者能继续被调度，不代表有实时等待上限。

以后看 ROS 控制循环时，先追问：共享了什么、临界区多长、等待会不会拖慢控制线程。暂不把“无锁”当成通用答案。
